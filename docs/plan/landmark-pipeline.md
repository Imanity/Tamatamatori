# 地标批量制作与接入

2026-11-08，按用户要求从逐个硬编码转换改为批量流程，以已下载的 Void 东京塔为样例。先提供较完整的下载候选清单，再把来源登记、检查、转换、数值验证、目录集成和后续画面验收分开。原始文件留在本地，静态站点仅携带合格的衍生产物，不增加后端或运行时 glTF 引擎。本轮不进行浏览器验证，不默认提交推送。

## 本轮范围

1. 核实一批可下载、许可明确的地标候选，给出具体作者、页面、建议文件名、下载优先级和复杂度。候选不等于已实现；已下载的晴空塔、上海中心、东京塔无需重下。
2. 以 JSON 配方保存来源哈希、许可核查、坐标框架、朝向、尺度、WGS84 锚点、粗分部对应和转换预算，避免每加模型修改转换器、加载器和 About。
3. 命令行扫描整个输入目录，生成检查报告；一条命令转换多个已登记配方，逐项记录失败，失败项不能污染应用目录。
4. CPU 几何、轮廓覆盖、大小和哈希合格后，预览集成计划，再成组更新资源、运行时目录和版权摘要。已经验收的既有模型保留；几何或定位变化使旧画面验证失效。
5. `verify` 不依赖原始下载，可在 CI 校验已集成资源、注册信息、生成文件及署名一致性。制作报告和原始文件放忽略目录。
6. 东京塔完成批量制作样例、近处粗分部替换和同城双地标数值/GL 替身检查。浏览器/GPU 标为待验；不得据此声称画面或实景精度已通过。

## 验收边界

许可、数据来源、建筑身份、WGS84 锚点和朝向需要逐模型核查，不能根据文件名或最高轴自动宣告正确。检查器可以指出负轴、缩放、反射、材质假透空和未支持的动画/压缩；不猜测全球模型的地理坐标或擅自放宽预算。

自动检查覆盖混合成功/失败批次、配方/源/产物篡改、生成文件漂移、路径边界、缺测配置、错误框架、重复 ID、未验画面状态及可复现生成；执行应用全部测试与子路径构建。后续下载更多模型时沿用同一命令及准入门槛，资料未补齐的项保持待处理。

## 下载与制作步骤

完整候选见[18 份下载清单](landmark-downloads.md)，也可使用 [CSV](landmark-downloads.csv)。原始下载集中放在默认下载目录或 `.cache/landmarks/inbox/`；文件名可以保留网站默认值，已有配方按文件内容哈希匹配。

```powershell
# 列出候选；先集中下载，不需要边下载边转换
npm run landmarks -- list
npm run landmarks -- inspect --input-dir C:/Users/TangRJ/Downloads

# 新文件的草稿示例：只输出忽略目录，保留未核查状态
npm run landmarks -- draft --id=oriental-pearl --input=C:/Users/TangRJ/Downloads/oriental-pearl.glb
```

检查报告在 `.cache/landmarks/inspection/<源哈希>.json`，包含实际面数、本地/世界包围盒、每个网格的矩阵、反射、材质透明模式和纹理数量。`draft` 从候选表填写作者、页面、许可和实际文件哈希，轴向、尺寸、机位及核查布尔值仍待填写；不会覆盖已有草稿，也不会自动加入应用。

逐份完成必要的人工核查后，将草稿保存到 `landmarks/recipes/<id>.json`。可对照[东京塔完整配方](../../landmarks/recipes/tokyo-tower.json)，核查要点如下：

- 来源：正式下载、作者、许可与上游声明；公开候选许可不能替代下载文件的核查。
- 框架：`space` 选 `local` 或 `world`；`axes` 顺序表示 ENU 三轴来自源模型的哪一个有符号轴。`local` 只在网格共享已核实的作者放置时使用；其他模型要保留节点世界变换或先烘焙。
- 尺度：`height` 对照官方尺寸；`center` 是轴变换后、统一缩放前的水平原点，或最低 0.01 源单位层的 `base-bounds` 中心。基座不等高的模型须显式给出中心，不能直接假定最低点可代表全基座。
- 定位：WGS84 纬经度、ENU 平面逆时针 `yawDegrees`、位置/朝向参考、近似误差及歧义；不根据模型文件名自动定位。
- 替换：按实际源瓦片核查 `id / height / base`；跨瓦片分部可单独填 `tile`。`parts: []` 的模型只能在普通建筑窗口之外应用，近处保留粗体块。避免把模型未包含的裙楼一起删掉。
- 处理：面数是目标，不保证简化器在误差限制内达到目标。`permissive` 允许跨法线接缝简化，焊接容差必须显式登记；减面仍须通过轮廓和预算检查。核查完成才把三项 `review` 设为 `true`。

完成多份配方后一次执行：

```powershell
# --all 指全部已核查配方；也可以 --ids=tokyo-tower,shanghai-tower
npm run landmarks -- batch --all --input-dir C:/Users/TangRJ/Downloads
npm run landmarks -- check --all
npm run landmarks -- integrate --all --dry-run --allow-pending-visual
npm run landmarks -- integrate --all --allow-pending-visual
npm run landmarks:verify
npm test
npm run build -- --base /Tamatamatori/
```

`batch` 对每项独立制作，错误不阻止其他模型继续检查，但批次最终以非零退出码报告未全部通过。`.cache/landmarks/last-batch.json` 汇总各项结果；单模型 `staging/<id>/` 保留报告、清单、压缩资源、六方向覆盖结果和原始参考几何。失败重跑会写入失败记录，不能沿用旧成功产物。可用 `--ids=成功项1,成功项2` 明确选择合格子批次；`integrate --all` 遇到任何不合格项整体拒绝写入。

`integrate` 不下载、不重新减面，只接受当前配方对应的暂存结果。它生成 `public/landmarks/*`、`landmarks/registry.json`、`src/data/landmarks.generated.json` 和 `public/landmarks/CREDITS.txt`，运行时目录、加载器和 About 无需逐模型手改。单文件通过临时文件替换，进程内写入异常会恢复此前文件；不保证进程被杀或断电时的跨文件事务。中断后先运行 `verify`，发现不一致时重新集成，不提交半套结果。

没有画面验收的新模型必须显式传入 `--allow-pending-visual`，并在右栏与 About 保留待验状态。默认命令不会把 CPU 检查升级为画面通过。本轮已获得用户暂缓浏览器的指示，因此东京塔保留待验。

## 更新与后续画面验收

改变资源或定位须提高配方 `version` 后重新制作，生成新文件名；旧资源不会自动删除。字节和定位未变化时，可以仅更新来源说明且保留旧模型画面证据。`verify` 检查配方/资源/注册与生成目录是否一致，正常 CI 构建已强制执行，不需要原始 GLB，也不会在 CI 访问 Sketchfab。

实际浏览器验收后，可将人工复核的 JSON 交给 `record-visual`：必须填写 `id`、当前注册的 `assetSha256` / `placementHash`、`gpuPassed: true` 与仓库内实际截图路径数组 `screenshots`。该命令登记既有证据，本身不运行浏览器；验收条件仍包含近/远景、长焦、手机视口恢复、失败回退及遮挡。

```powershell
npm run landmarks -- record-visual --id=tokyo-tower --evidence=docs/plan/landmark-pipeline-evidence/tokyo-gpu.json
```

上面是未来验收后的使用方式；本轮没有生成 `tokyo-gpu.json`，也没有执行该登记。批量制作脚本支持静态自包含 Float32 GLB；外部依赖、动画、骨骼、变形及未解码的几何压缩会明确拒绝，OBJ/FBX 等先离线整理，不声称所有下载都能自动准入。

## 东京塔样例执行结果

使用 Void / CC BY 4.0 的正式 GLB，源文件 15,881,704 B，实际 137,537 顶点 / 88,707 面。其本地 Z 轴向上，三个网格共享带倾斜及非均匀缩放的作者场景放置；本次使用共同本地框架，统一总高 333 m，四脚对照 OSM 拟合 56.25°，中心 RMS 约 2.12 m，近似对称朝向仍不唯一，见[注册记录](landmark-pipeline-evidence/tokyo-registration.json)。

首次 80,000 顶点门槛无法保留硬边，较激进的 0.1 m 接缝简化虽然压到 76,171 顶点，却因细杆丢失只有约 96.97%—97.87% 轮廓重合，已拒绝。最终显式将单资源顶点上限提高至 **128,000**，保留 **2 MiB gzip / 4 MiB 解压 / 100,000 面**限制，使用 0.02 m 的简化器误差参数；这不是实景几何误差承诺。

| 目标 | 顶点 | 三角面 | gzip 字节 | 解压字节 | 画面状态 |
| --- | ---: | ---: | ---: | ---: | --- |
| 晴空塔 | 65,576 | 88,581 | 1,236,544 | 2,636,828 | 既有模型验收保留，本轮未重验 |
| 上海中心 | 59,701 | 54,682 | 975,220 | 2,089,040 | 上阶段模型验收保留，本轮未重验 |
| 东京塔 | 120,057 | 74,767 | 1,225,486 | 3,778,604 | CPU/GL 替身通过，真实 GPU 待验 |

东京塔六方向 CPU 三角形覆盖 IoU 为 0.998903—0.999318，栅格覆盖差距最大约 0.372 m（0.1665 m/px），并非源资料绝对精度。晴空塔和上海中心迁入同一流程，压缩几何及解压哈希均与原版一致；三者重复批次生成结果一致。各模型覆盖与批次摘要见[执行结果](landmark-pipeline-evidence/results.json)。

[真实 MVT 单瓦片 CPU 回放](landmark-pipeline-evidence/tokyo-source-replay.json)确认东京塔七类分部，共 29 个多边形；保留 `42473133` / 20 m 的 FootTown。其他瓦片明确替换为空响应，基座使用合成 0 m 平地；两处东京地标同时应用，总 233,980 面。这个混合输入回放不能代表完整城市覆盖、真实 DEM 或 GPU 画面。

267 项自动检查通过，`/Tamatamatori/` 子路径构建、三次批量制作的一致性及 163 处本地文档链接已核对，结果见执行摘要；实际浏览器、手机画面和帧率本轮未执行。下一步可按下载清单集中收集文件，然后批量完成来源/尺度/朝向核查与制作，再统一做画面验收。
