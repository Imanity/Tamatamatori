# 空间站构图首步

## 范围

接入 ISS（NORAD 25544）与天宫天和核心舱（48274），提供独立图层、按拍摄 UTC 时刻推算的位置标记、前后各三分钟的轨迹点、目标朝向、地形遮挡与轨道数据状态。空间站按目录身份选取，避免将停靠飞船、实验载荷或同一组合体的模块重复展示。

轨道来自 CelesTrak stations 分组的 GP JSON，使用固定 satellite.js 7.1.0 的 SGP4。实测接口 HTTP 200，但缺少浏览器跨域许可，因此由 GitHub Actions 获取并发布同源 JSON。保持静态站点架构。完整署名加入 About。

## 数据更新

- Actions 计划每三小时检查一次，UTC 第 23 分触发，推送及手动工作流也检查。两次上游请求至少相隔两小时，使用持久缓存保存尝试时间和最近有效数据。
- 只由发布构建任务请求上游，PR 和其他 Node.js 验证任务不请求。请求失败（HTTP 错误、响应过大、格式无效、没有任何所选空间站）停止自动重试，保留旧数据并发布明确的失败状态，维护者处理后手动恢复。
- 上游完全没有应答（连接失败、DNS、超时、响应中途断开）不算数据问题，不暂停：保留已发布轨道，在 `notice` 与 CI 警告中写明，冷却后由下一次定时检查重试。手动恢复时仍无应答，则保持原来的暂停。2026-11-12 起采用，见[暂停恢复](#暂停恢复2026-11-12)。
- 某个空间站在上游的历元早于已发布版本，或本次响应缺少它时，不算失败：保留该站较新的已发布轨道，其余照常更新，在快照的 `notice` 与 CI 警告中写明，下一次检查照常进行。2026-11-09 起采用，见[暂停排查](#暂停排查2026-11-09)。
- 暂停时站点照常发布，CI 仍为成功，只有警告注释，GitHub 不会因此发通知。发布后的“数据源暂停提醒”任务（`scripts/feed-alerts.mjs`）读取站点实际提供的快照：进入暂停时自动开一个 Issue（提及仓库所有者，写明错误、时间、当前历元与恢复步骤），暂停期间不重复开；恢复后留言并关闭。未暂停但超过 24 小时没有成功更新（例如上游持续无应答）时，同样开一个 Issue，标题与说明不同，成功更新后关闭（2026-11-12 起）。只有这个任务有写 Issue 的权限，读不到已发布数据时不开也不关。2026-11-09 起采用。
- 网页开启图层后每五分钟检查同源快照，后台暂停，回到前台检查到期数据。手动按钮刷新已发布快照，不能强制上游突破更新间隔。
- 分别展示轨道历元、上游成功检查、上游尝试及网页检查时间。刚下载并不意味着轨道历元变新。
- 距轨道历元超过 24 小时提示低可信，超过 72 小时停止位置与轨迹绘制。该范围是本应用的显示策略，不能解释为 SGP4 精度保证。未来和历史时刻采用相同边界。
- 变轨时间和新解发布存在延迟。不能通过旧轨道提前识别所有变轨，也不能将下载成功表述为已校正变轨。拍摄前重新检查数据，变轨后等待新历元。

GitHub 定时任务可能延迟，公开仓库长期无活动也可能停用计划任务。因此界面以实际检查时间与轨道历元判断新鲜度，超过六小时未成功检查时显示提示。定时流程在本轮工作流部署后启用，首次远端执行需单独核对。[GitHub 定时任务说明](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

## 验收

固定 GP 输入对照独立 SGP4 与地平坐标，检查经纬度、极区、跨日、传感器视场、实际相机高度和折射。检查缺失、非数、过期、更新回退、取消、后台恢复及冷却。用替身检查异步遮挡与资源生命周期，刷新 Chrome 核对标记、轨迹、视场外/地平线下、遮挡和错误状态。

## 使用与边界

位置环及轨迹点属于构图标记，轨迹点间隔十秒，秒级拍摄位置可用右侧按钮调整。地影参考使用几何阴影估计，可拍摄性还取决于天空亮度、光学条件及实际轨道误差。当前开放 ISS 与天宫核心舱两个目录身份。

上游暂停后，维护者先核对具体错误，再在手动 CI 中勾选 `resume_orbits`。本地可以运行 `npm run update:orbits -- --resume`，仍须等待两小时冷却。本地成功检查后提交的仓库快照更新时间最新，推送后 CI 会选用它，同样能解除已发布快照的暂停。

## 暂停排查（2026-11-09）

- **现象**：已发布快照自 2026-11-07 05:28 UTC 起处于暂停状态，错误为“轨道历元回退”。轨道停在 ISS 2026-11-06 11:57、天宫 11-06 02:56；到 11-09 19:20 已超过 72 小时，网站停止绘制空间站。
- **原因**：
  - 那次检查（CI 运行 42342840548），CelesTrak 为至少一个空间站返回了早于已发布快照的历元。11-06 23:29 的上一次成功检查已取得上述较新的历元。
  - `assertOrbitProgress` 把单个目标的历元回退当成整次更新失败，于是写入错误并暂停。此后每次定时任务都因暂停而跳过，没有自动恢复的途径。
  - 上游当时为何返回旧历元无法追溯（响应未保存），可能是上游副本未刷新或重新拟合。11-09 再查时，CelesTrak 已提供 11-09 的历元（ISS 04:58、天宫 01:33），回退只是暂时的。
- **修复**：
  - `scripts/update-stations.mjs` 逐站比较：上游历元较旧或缺少该站时，保留已发布的较新轨道，并在 `notice` 中记录站名与两个历元，状态仍为成功、不暂停。
  - `assertOrbitProgress` 保留，作为发布快照不回退的最后检查。浏览器读取到较旧的已发布副本时，仍沿用本地较新的数据。
  - HTTP 错误、无效数据等真正的上游问题仍按原规则暂停。
- **验证**：
  - 空间站测试 9 项通过。新增一项：历元回退时保留较新轨道、记录说明、不暂停，下一次检查用更新的历元；缺少某站时保留其轨道；`notice` 格式校验。原有的 HTTP 和无效数据暂停测试保持不变。
  - 用一次真实 CelesTrak 请求做了两组恢复：已发布的暂停快照加 `--resume`，以及仓库快照正常检查，两者都得到 11-09 的历元，状态成功、无说明。
  - 仓库快照 `public/orbits/stations.json` 已写入这次检查结果，推送后 CI 会选用它，无需再手动恢复。
- **通知**：这次暂停持续两天多却没有任何提醒，因为更新失败时 CI 仍按成功结束。为此新增“数据源暂停提醒”任务，见上文“数据更新”。对当时仍处于暂停的已发布快照做只读演练，计划正确：为空间站开一个 Issue，彗星不动；没有实际创建。测试 3 项覆盖开、不重复、关闭、读不到时不动、只认机器人带标记的 Issue、接口调用与演练模式，以及权限只给这个任务。下一小步适合补充未来短时过境的时段列表，沿用本轮历元与更新状态约束。

## 暂停恢复（2026-11-12）

- **现象**：2026-11-11 06:47 UTC 的定时任务访问 CelesTrak 时在网络层失败（`fetch failed`，约 10 秒后报错，没有 HTTP 状态），按现行规则暂停。提醒任务随即开了 Issue #1。轨道停在 ISS 11-10 04:12、天宫 11-10 00:34；按 72 小时停绘规则，网站将于 11-13 约 04:12 UTC 不再绘制空间站。
- **处理**：11-12 03:40 UTC 按 Issue 中的恢复步骤，在本地运行 `npm run update:orbits -- --resume`，一次请求成功：ISS 历元 11-11 08:03、天宫 11-11 14:56，状态成功、无说明。新快照写入仓库，推送后 CI 选用它（尝试时间最新），提醒任务确认恢复后关闭 Issue。
- **规则调整**（用户同日确认）：
  - 上游没有应答（连接、DNS、超时、响应中断）时，不再暂停，只沿用已发布数据并记录说明，下一次定时任务重试。HTTP 错误与无效数据仍暂停。
  - 判断集中在 `scripts/lib/transport.mjs`，空间站与彗星共用；彗星的单个请求在本次运行内先按 5xx 的方式重试两次。
  - 为免持续无应答没人知道，提醒任务在超过 24 小时没有成功更新时也开 Issue。
  - 测试新增 3 项：两个数据源的无应答、超时、响应中断与无效数据对照，以及 24 小时提醒的开启、不重复与关闭。用已发布数据做只读演练，两者都为正常运行。
